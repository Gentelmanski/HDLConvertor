# HDLConvertor — конвертер VHDL, Verilog и SystemVerilog

HDLConvertor — исследовательский прототип настольного приложения для **преобразования описаний цифровой аппаратуры** между языками **VHDL**, **Verilog** и **SystemVerilog**. Проект **изначально создан и разрабатывался в Qt Creator** на **C++17** с использованием **Qt 6 Widgets**. Для конфигурации и сборки используется **CMake** (`CMakeLists.txt`), а Qt Creator выступает средой разработки (IDE), в которой проект можно открывать, редактировать, собирать и запускать.

Проект ориентирован на небольшие синтезируемые HDL-модули и демонстрацию подхода к трансляции исходного кода через общее **промежуточное представление (IR)**. Это **не полноценный компилятор всех трёх языков**: поддерживается ограниченное подмножество конструкций, причём направления конвертации реализованы несимметрично.

## Интерфейс программы

![Графический интерфейс HDLConvertor: исходный VHDL и результат на Verilog](docs/images/interface-demo.png)

*Скриншот из научно-исследовательской работы: пример конвертации двухвходового логического элемента AND. Внешний вид зависит от темы Qt и операционной системы.*

В главном окне доступны:

- выбор исходного и целевого языков (`VHDL`, `Verilog`, `SystemVerilog`);
- два редактора — для исходного кода и сгенерированного результата;
- кнопка **«Проверить синтаксис»** — запуск встроенного парсера и вывод диагностики;
- кнопка **«Конвертировать»** — разбор исходного текста и генерация целевого HDL;
- кнопка **«⇄ Поменять»** — смена направлений (если есть результат, дополнительно меняются местами тексты редакторов);
- кнопки **«Пример»** (загружает демонстрационный VHDL-код AND) и **«Очистить»**;
- панель **«Диагностика»** для сообщений уровней `Info`, `Warning`, `Error`, в том числе с координатами, когда они известны.

> **Важно:** «Проверить синтаксис» означает проверку реализованным в приложении *ограниченным парсером*, а не полную проверку соответствия стандартам IEEE. Для проверки сгенерированного HDL рекомендуется использовать отдельный симулятор или компилятор целевого языка.

## Быстрый старт

### Требования

- **Qt Creator** — рекомендуемая среда разработки для этого проекта (для сборки из терминала необязателен);
- **CMake 3.16+**;
- компилятор с поддержкой **C++17** (MSVC, GCC или Clang);
- **Qt 6** с компонентом **Widgets**, заголовочными файлами и CMake-конфигурацией Qt;
- генератор CMake, совместимый с выбранным компилятором (например, Ninja, Make или Visual Studio).

### Сборка и запуск в Qt Creator (основной способ)

1. Установите **Qt Creator**, **Qt 6** (модуль **Qt Widgets**), CMake и совместимый компилятор. В Qt Creator должен быть настроен комплект сборки (**Kit**), соответствующий установленной версии Qt и компилятору.
2. Распакуйте архив проекта. В Qt Creator выберите **File → Open File or Project** (в некоторых версиях меню называется **File → Open Project**), затем укажите **`CMakeLists.txt`** в корне проекта. Открывать отдельный `.cpp` вместо файла проекта не нужно.
3. В окне **Configure Project** выберите подходящий **Desktop Kit** с Qt 6 и конфигурацию **Debug** или **Release**, затем нажмите **Configure Project**. Qt Creator запустит CMake и определит исходные файлы из `CMakeLists.txt`.
4. Выполните **Build → Build Project** (`Ctrl+B` в Windows/Linux; `Cmd+B` в macOS).
5. Запустите программу кнопкой **Run** или сочетанием `Ctrl+R` в Windows/Linux (`Cmd+R` в macOS). Точка входа — `main.cpp`, исполняемая цель CMake — **`VHDLVerilogConverter`**.

Если Qt Creator сообщает, что пакет `Qt6` не найден, проверьте установленную версию Qt и выбранный **Kit** в настройках **Preferences → Kits** (название раздела может отличаться в зависимости от версии IDE). Qt Creator обычно размещает результаты сборки **в отдельной build-директории**, поэтому путь к исполняемому файлу при сборке через IDE может отличаться от команд в следующем разделе.

### Сборка из терминала (альтернативный способ)

Выполняйте команды из **корня проекта**, где расположен `CMakeLists.txt`:

```bash
cmake -S . -B build
cmake --build build --config Release
```

**Linux / macOS** (для одноконфигурационных генераторов):

```bash
./build/VHDLVerilogConverter
```

**Windows / Visual Studio** (типичный путь для многоконфигурационного генератора):

```powershell
.\build\Release\VHDLVerilogConverter.exe
```

При использовании Ninja на Windows исполняемый файл обычно находится прямо в `build/`. Конкретный путь зависит от генератора и конфигурации. В Windows необходимо также обеспечить доступность библиотек Qt при запуске (например, настроить Qt kit в Qt Creator или развернуть необходимые DLL средствами Qt).

Если CMake не находит Qt 6, передайте путь к установленному Qt:

```bash
cmake -S . -B build -DCMAKE_PREFIX_PATH="<путь-к-Qt/6.x/компиляторному-kit>"
```

> В предоставленном обновлённом архиве `CMakeLists.txt` ссылался на `src/main.cpp`, `src/parser.cpp` и другие пути внутри `src/`, хотя исходники размещены в корне. **В прилагаемом архиве с документацией эти пути исправлены**. Остальные `.cpp` и `.h` не изменялись. Фактическую сборку в этой среде проверить не удалось, поскольку Qt 6 Widgets здесь не установлен.

## Как пользоваться

1. Запустите `VHDLVerilogConverter`.
2. Выберите **исходный язык** и **целевой язык** в верхней панели.
3. Вставьте код модуля в левый редактор «Исходный код» или нажмите **«Пример»**.
4. По необходимости нажмите **«Проверить синтаксис»** и прочитайте сообщения внизу окна.
5. Нажмите **«Конвертировать»**. При ошибках разбора конвертация отменяется; иначе результат выводится справа.
6. Проверьте полученный текст средствами целевого HDL, особенно если в диагностике есть предупреждения.

Приложение не содержит встроенного диалога импорта/экспорта HDL-файлов: текст можно копировать из редакторов и сохранять в обычном редакторе исходного кода.

### Пример: VHDL → Verilog

**Вход — VHDL:**

```vhdl
library ieee;
use ieee.std_logic_1164.all;

entity and_gate is
    port (
        a : in std_logic;
        b : in std_logic;
        y : out std_logic
    );
end entity and_gate;

architecture rtl of and_gate is
begin
    y <= a and b;
end architecture rtl;
```

**Ожидаемый смысл результата — Verilog:**

```verilog
module and_gate (
    input wire a,
    input wire b,
    output wire y
);
    assign y = a & b;
endmodule
```

Это иллюстрация семантически соответствующего кода; конкретное форматирование, комментарии и расположение объявления портов определяет генератор текущей версии.

## Архитектура и принцип работы

![Архитектура: лексер, парсер, IR, генератор и диагностика](docs/images/architecture.png)

*Архитектурная схема из НИР «Исследование методов преобразования описаний цифровой аппаратуры между языками VHDL, Verilog и SystemVerilog и разработка прототипа конвертера».*

Процесс преобразования:

1. **`Lexer`** (`lexer.h`, `lexer.cpp`) — выделяет лексемы входного текста: ключевые слова, идентификаторы, литералы, операторы и знаки пунктуации.
2. **`Parser`** (`parser.h`, `parser.cpp`) — интерпретирует токены в контексте выбранного HDL. Для VHDL реализован более широкий разбор, чем для Verilog/SystemVerilog.
3. **`IRModule`** (`ir.h`) и **выражения** (`expr.h`) — описывают модуль независимо от синтаксиса конкретного языка: параметры, порты, сигналы, присваивания, процессы, экземпляры модулей и часть выражений и управляющих конструкций.
4. **`Converter`** (`converter.h`, `converter.cpp`) — преобразует IR в текст VHDL, Verilog-2001 или ограниченного SystemVerilog.
5. **`Diagnostic`** (`diagnostic.h`) — хранит уровень, строку, столбец и текст сообщений; **`MainWindow`** (`mainwindow.h`, `mainwindow.cpp`) показывает их пользователю.

Общее IR позволяет отделить разбор каждого исходного языка от генерации целевого. В отличие от буквальных замен текста конвертер оперирует структурными элементами описания, хотя семантический анализ и охват стандартов пока неполные.

### Как это соотносится с типичной структурой Qt Creator

**Qt Creator не требует единственной жёсткой структуры каталогов.** При создании стандартного проекта **Qt Widgets Application** мастер обычно формирует `CMakeLists.txt`, `main.cpp`, файлы класса окна (`mainwindow.h`, `mainwindow.cpp`) и форму `mainwindow.ui`. Дополнительно в приложениях могут использоваться ресурсы `.qrc`, а в крупных проектах исходники часто распределяют по папкам `src/`, `include/`, `tests/` с отдельными `CMakeLists.txt`. Последний вариант — способ организации проекта, **не обязательное правило Qt Creator**.

Пример **типовой, но не обязательной** структуры небольшого приложения с формой Qt Designer:

```text
ExampleQtWidgetsApp/
├── CMakeLists.txt       # Описание сборки (если выбран CMake)
├── main.cpp             # QApplication и запуск главного окна
├── mainwindow.h         # Объявление класса окна
├── mainwindow.cpp       # Логика класса окна
├── mainwindow.ui        # Форма Qt Designer (если интерфейс создан в Designer)
└── resources.qrc        # Ресурсы (необязательный файл)
```

**В HDLConvertor всё устроено иначе, и это корректно:**

- **Файлы `.cpp` и `.h` лежат непосредственно в корне** репозитория, а не в `src/`. CMake может работать с любым расположением, если пути в `CMakeLists.txt` ему соответствуют. Поэтому **в документированной версии архива исправлены пути в CMake**, а перенос исходников ради «стандартной» структуры не выполнялся.
- **Файла `mainwindow.ui` нет**, поскольку интерфейс создаётся **программно** в `MainWindow::setupUi()` (`mainwindow.cpp`): используются `QMainWindow`, `QPlainTextEdit`, `QComboBox`, кнопки и компоновщики Qt Widgets. В CMake по этой причине установлен `CMAKE_AUTOUIC OFF`.
- **`CMAKE_AUTOMOC ON` необходим**, поскольку `MainWindow` наследуется от `QMainWindow` и объявлен с макросом `Q_OBJECT`: Qt автоматически генерирует соответствующий meta-object-код при сборке.
- **Файла `.pro` нет и он не нужен**: это формат системы сборки *qmake*, тогда как HDLConvertor использует *CMake*.
- **Файл `.qrc` отсутствует**: иллюстрации в `docs/images/` используются в README на GitHub и не являются ресурсами, встраиваемыми в исполняемый файл. В CMake задан `CMAKE_AUTORCC OFF`.
- Файлы **`CMakeLists.txt.user` / `.qtcreator/` с локальными настройками**, а также build-каталоги могут создаваться Qt Creator на конкретном компьютере. Они **не являются частью исходного кода** и обычно не публикуются в Git. Файл `.gitignore` проекта уже содержит правила для `CMakeLists.txt.user*` и результатов сборки.

При дальнейшей разработке допустимо вынести исходники в `src/`, но тогда нужно **одновременно обновить пути и/или `add_subdirectory()` в CMake**. Для текущего объёма проекта плоская структура вполне подходит; специальная реорганизация для Qt Creator не требуется.

## Текущее состояние и ограничения

Фактические возможности в данном разделе определены по исходному коду, а не только по целям, сформулированным в НИР.

| Возможность | Статус в исходном коде |
| --- | --- |
| Графический интерфейс, выбор языков, редакторы, диагностика | Реализованы |
| Разбор VHDL entity/architecture, портов, сигналов, присваиваний | Реализован для ограниченного подмножества |
| Часть VHDL process, if/case, with/select и экземпляров | Есть обработка, требуется проверка на конкретных случаях |
| Разбор Verilog/SystemVerilog | Упрощённый: заголовок `module`, параметры, ANSI-порты, сигналы и `assign`; полноценного разбора процедурных блоков нет |
| Генерация VHDL и Verilog | Реализована на основе доступных элементов IR, с ограничениями по типам и поведению |
| Генерация SystemVerilog | Преимущественно Verilog-подобный вывод с `logic`, `always_ff` и `always_comb` |
| Полная совместимость со стандартами IEEE 1076 / 1364 / 1800 | Не реализована |
| Автоматическая формальная эквивалентность, интеграция GHDL / Yosys / cocotb | В проекте отсутствуют; описаны в НИР как методика проверки и направление развития |

**Особенности, на которые стоит обратить внимание:**

- При исходном и целевом языке, выбранных одинаково, `Converter::convert()` возвращает пустой результат и сообщение-предупреждение.
- Встроенный анализ Verilog/SV не охватывает полноценно `always`, `always_ff`, `always_comb`, вложенные конструкции и многие элементы языка. Некоторые конструкции могут не попасть в IR и, следовательно, не появиться в результате.
- В текущем IR нет полной семантической модели всех типов, знаковости, правил расширения разрядности, временной модели и множественных драйверов. **Нельзя считать любое преобразование поведенчески эквивалентным без проверки.**
- В НИР сформулирован принцип **«ничего не терять молча»**. Он является важной целью архитектуры, но фактическая реализация не гарантирует диагностику *каждой* неподдерживаемой конструкции.
- В архиве отсутствуют автоматические тесты и настроенные проверки внешними HDL-инструментами.

## Проверка корректности преобразования

![Методика проверки: синтаксис, формальная эквивалентность и совместная симуляция](docs/images/verification-workflow.png)

*Методика проверки, предложенная в НИР. Это схема рекомендованного процесса, **а не реализованная в приложении автоматическая функция**.*

Для реального HDL-проекта проверять результат рекомендуется на трёх уровнях:

1. **Синтаксис:** VHDL — `GHDL`; Verilog — `Icarus Verilog`; Verilog/SystemVerilog — `Verilator` (с учётом поддерживаемых ими конструкций).
2. **Эквивалентность:** сравнение исходного и полученного модулей на уровне поведения или синтезированной логики, например с помощью инструментов на базе `Yosys` при наличии соответствующих фронтендов.
3. **Симуляция:** одинаковые тестовые воздействия на исходный и преобразованный модуль, сравнение выходных последовательностей; для сценариев может использоваться `cocotb` вместе с соответствующими симуляторами.

Этот процесс позволяет обнаружить ошибки, которые не выявляет одна лишь синтаксическая проверка: например, изменение ширины сигнала или некорректное поведение последовательностной логики.

## Возможные направления развития

- Расширить грамматики Verilog и SystemVerilog, включая процедурные блоки и управляющие конструкции.
- Уточнить семантику выражений, правила преобразования ширин, знаковости и типов.
- Реализовать систематическую диагностику неподдерживаемых конструкций без потери фрагментов кода.
- Добавить набор воспроизводимых HDL-тестов и запуск внешних компиляторов/симуляторов.
- Добавить проверку функциональной эквивалентности и сравнение результатов симуляции.
- Поддержать открытие и сохранение HDL-файлов из интерфейса.
